# VocabularyApp Stage 2 Part 3 优化方案

主题：在线查词与候选释义录入辅助  
整理日期：2026-10-07  
状态：历史规划与选型过程；功能定位现已确认，当前开发交接以 [Stage 2 Part 3 工作提示词](VocabularyApp-Stage2-Part3-Work-Prompt.md) 为准。本对话本次仅整理文档，未执行正式应用开发或部署。

最新决定：用户在两轮测试后接受有道通用 NMT 翻译参考、独立修改查询短语及人工修订确认保存。下文保留早期选型讨论；“正式范围尚待明确”等历史表述已由该决定更新。新的代理平台、费用与部署凭据仍需在具体方案中处理。

## 1. 阶段依据与目标

Stage 2 Part 2 已交付应用 1.1.0，实施记录见 [完成报告](stage2-part2-report.md)。本对话已阅读报告并抽查关键实现，未重新运行完整测试或核验线上发布。用户随后明确反馈：生成的约 30 词电子信息测试词库导入测试通过。这证明了此次用户侧导入操作成功，不代表在线查词、释义质量或所有设备均已通过验证。

下一阶段目标是减少阅读论文时往返外部查词和手动录入的成本：

> 查询个人词库 → 用户主动在线查词 → 查看候选释义 → 选择并修订中文释义 → 确认保存到个人词库。

中文释义和专业语境仍是核心目标。第三方结果只作为候选；不能自动决定 substrate、bias、carrier 等多义词的最终含义。现有手动添加、离线本地检索与 JSON 备份继续完整可用。

## 2. 范围与实施顺序

| 步骤 | 必须完成的工作 | 交付物 |
| --- | --- | --- |
| 3A：来源验证 | 对比公开接口能力、30 词覆盖、网络可用性、费用与许可，明确接入路径 | `docs/stage2-part3-provider-evaluation.md` |
| 3B：功能实现 | 接入选定来源，完成候选选择、编辑、保存及故障处理 | 应用 1.2.0 与阶段报告 |
| 验收 | 原功能回归、数据保护、并发查询、网络故障、输入法与实际设备检查 | 可复现的结果与验证边界 |

先完成 3A，再依据实际结果确定 3B 的来源。此方案未指定一个已经实测可用的中文服务，也未承诺任何第三方免费额度。

本阶段不加入标签、论文来源字段、PWA、账号、云同步、AI 翻译、PDF 导入、自动背词、语音播放或整库在线查询。不为尚未确定的后续功能重构数据库。

## 3. 来源验证：先解决可行性

### 3.1 已核对的官方资料

以下信息核对于 2026-10-07；实际接入时仍需复核文档和条款。

| 候选 | 官方资料能证明的能力 | 仍需验证的内容 |
| --- | --- | --- |
| Free Dictionary API | 官方示例使用英文词条接口，返回英文定义、词性和部分例句 | 专业词和短语覆盖、浏览器跨域、用户网络可达性、数据许可及展示要求；它不能直接承担中文释义目标 |
| 有道文本翻译 API | 文档支持中英翻译，要求应用 ID 和私密密钥参与签名 | 多义词/专业术语质量、费用、条款、额度及服务端接入；翻译结果不等同于完整词典多义项 |

官方来源：

- [Free Dictionary API](https://dictionaryapi.dev/)
- [有道文本翻译 API](https://ai.youdao.com/DOCSIRMA/html/trans/api/wbfy/index.html)
- [Vite 环境变量说明](https://vite.dev/guide/env-and-mode)：浏览器代码使用的 `VITE_*` 值会进入客户端构建；不能用前端环境变量隐藏私密密钥。

可继续查找其他官方、授权可用的来源。避免依赖逆向网页私有接口、未经许可的抓取或公共跨域代理作为正式方案。

### 3.2 测试词集合

使用本次已生成的 30 词，记录每个词的独立查询结果：

substrate、bias、permittivity、permeability、susceptibility、impedance、capacitance、inductance、conductivity、resistivity、semiconductor、bandgap、carrier、carrier mobility、depletion region、threshold voltage、leakage current、transistor、dielectric、attenuation、bandwidth、resonance、signal-to-noise ratio、electromagnetic interference、sampling frequency、aliasing、transfer function、transient response、steady state、trade-off。

本次生成的中文释义属于演示参考，不作为词典质量的唯一权威答案；专业含义由用户结合论文语境判断。

每个词至少记录：

- 查询时间、来源、请求成功或失败、实际耗时。
- 是否有中文候选、是否只是英文定义、是否支持完整短语。
- 专业含义是否可用，是否误用了日常语义；没有结果也如实计入。
- 结果是否支持选择和编辑，以及必要的署名、许可和保存限制。

分开报告“请求成功率”“有结果比例”“有中文比例”“专业释义可用比例”，不能只用 HTTP 成功率代表产品可用性。建议质量目标为至少 24/30 有可用中文候选；这是评估目标，不是对外保证，也不是通过自动测试即可判定的事实。

测试必须区分命令行调用与真实浏览器调用。纯前端路径需要在 localhost 和真实 Pages 环境验证 HTTPS、跨域与特殊字符编码。国内网络可用性需在用户实际网络验证；自动化环境能访问不代表用户一定能访问。

没有可用账户或密钥的服务，记为“仅文档评估，未实测”；不能凭空补测试数据或将模拟响应视为服务质量结果。

### 3.3 接入决策规则

优先选择满足需求、授权清楚、无需私密密钥且浏览器可直接访问的来源。不要只为维持纯前端架构而把英文定义宣传成中文专业释义。

若合适来源需要私密密钥，可提出最小服务端代理方案：密钥仅保存在服务端，包含请求长度限制、超时、服务端限流、额度上限、固定上游与错误处理。CORS 只能约束浏览器请求，不能单独防止公开代理被滥用。该路径不需要上传或云端保存个人词库，但会新增运维和潜在费用。

建立付费服务、充值、使用私人凭据或部署新的服务端资源，需要用户针对具体方案授权；本次生成方案不包含这些动作。已授权的只读研究和无费用验证可以继续完成。

若没有符合成本与质量要求的来源，完成评估报告，明确提供三种可选路径：接受服务端与费用；采用“英文参考＋手填中文”的缩小范围；暂缓查词并转向标签/来源。后两者属于范围调整，不能悄悄按原目标发布并宣称完成。

## 4. 查询入口与候选展示

2026-10-07 已收到有道通用版 30 词本机实测，30 次均返回有效中文翻译，中位耗时 214 ms；至少 substrate、bias、bandgap、carrier 的返回不适合目标专业语境。详细结论见 [来源初步评估](stage2-part3-provider-evaluation.md)。该结果证明本次接口调用正常，不能替代专业质量审阅或正式来源决策。实现前须明确功能定位是翻译参考，还是完整词典候选义项；其余规范按选定范围执行。

同日第二轮 24 项语境对照均返回翻译，中位耗时 215 ms。部分短语有效改善，但 gate bias 仍返回“门偏见”。两轮结果支持将有道用于人工确认的翻译参考；尚不足以认定完整专业词典目标已实现。若采用翻译参考路径，建议查询文本与保存英文词条分开编辑并明确显示实际请求，不能自动裁剪短语翻译或覆盖原词。正式范围尚待明确。

### 4.1 入口

- 新增词条表单提供“在线查词”按钮，使用当前英文输入作为查询内容。
- 本地搜索无结果时保留“新增词条”，可以进入预填英文的新增表单后查词。
- 本地搜索仍按现有英文、中文和备注规则工作，不因键入字符自动发起外部请求。
- 当前筛选可能隐藏已有词条；保存时仍必须检查全库重复，不能以当前结果为空判断未收录。
- 编辑词条可沿用同一查词组件，但查询不能直接替换现有释义或备注；如实现成本较高，首版仅开放新增入口，并在报告注明。

### 4.2 展示

显示查询词、来源、结果语言，以及来源实际提供的词性、候选定义和例句。没有提供的字段不推测、不伪造。不把单一翻译结果包装成多个词典义项。

优先呈现中文候选；英文参考须明确标识语言。每个候选提供“采用此释义”，采用后进入可编辑的中文释义输入框，不自动提交。首版采用单项选择，用户可以在输入框中补充其他义项，不新增复杂的多选合并系统。

来源要求的署名和链接必须显示；允许缓存、保存、导出或修改的边界应在选型时明确。保存或导出若涉及许可要求，按条款保留必要信息，不以隐藏来源规避要求。

页面只呈现文本，不执行来源返回的 HTML。外部链接只允许经过校验的 HTTPS 地址。首版不嵌入第三方网页、音频或脚本。

## 5. 保存与现有数据规则

- 用户选择候选后，可以自由修订中文释义，再使用原有“保存”或“保存并继续添加”。
- 查询、显示候选、选择候选、取消与查询失败均不修改词库，也不增加备份 revision。
- 用户已有未保存的释义，采用候选前必须明确提示替换；取消替换保留原文。查询过程始终保留英文、释义和备注输入。
- 例句和来源不会偷偷追加到用户备注。若需要保存，提供明确的追加动作并保留原备注；不加入专用来源字段。
- 英文仍使用 `trim + lowercase` 去重，保存通过现有 Service / Repository 及事务执行。
- 保存成功后的 revision、学习状态、连续添加焦点与清空规则沿用 1.1.0；保存失败保留输入。
- 同名词保留原记录，不因在线结果自动覆盖；重复时可以按现有流程查看或编辑已有记录。
- 词典返回其他拼写或词形时，先展示差异，不自动改写用户输入的英文词条。
- 后续查看已保存词条不会自动请求第三方服务，也不需要第三方服务才能显示内容。

## 6. 请求行为与错误恢复

实现清楚的空闲、查询中、有结果、无结果、失败状态。查询中显示反馈，不能出现无限等待。

初始建议配置：单次查询超时 10 秒，查询文本最多 200 个字符；均集中配置，实际来源若要求更严则遵循来源限制。查询长度限制只限制在线调用，不擅自改变现有手动录词或历史导入规则。

- 只在用户主动操作时查询；同一查询进行中不重复发送，不自动连续重试。
- 新查询取代旧查询时取消旧请求，同时用请求标识防止取消不及时的旧响应覆盖新结果。
- 用户修改查询词、关闭弹窗或连续保存开始下一条后，旧请求失效，旧候选不残留到新词条。
- 请求失败不清空输入，提供手动重试和继续手动添加。
- 区分无结果、离线/网络失败、超时、限流、鉴权或额度问题；展示用户能理解的提示，不泄露密钥或原始服务端堆栈。
- 验证响应类型与字段结构，限制响应大小和候选展示数量；具体上限根据选定接口实测记录。
- 无结果不自动换成短语中的单词或错误纠正结果。若未来提供拆词查找，应由用户主动选择。

## 7. 隐私、存储与架构

查词入口说明：“在线查词会将当前英文词或短语发送至所示服务。”第三方也可能获得请求相关网络信息。不要承诺绝对匿名。

不发送个人词库、中文释义、备注、备份、查看统计或数据库标识。不要添加将查询词发送给额外分析服务的统计代码，不在生产日志记录完整用户查询。

默认只在组件内存中保留当前结果，不新增持久缓存。需要缓存时先检查许可，限定容量和过期时间，并使用 VocabularyApp 专属命名空间。

架构保留 React → Service → Repository 的本地数据写入路径。第三方接口放入独立 Provider / 查词服务，向界面返回稳定的小型候选模型；不要为一个来源引入大型插件框架。

原则上继续使用 `VocabularyDB`、Dexie schema 2、JSON version 1 和现有词条字段。在线查询没有数据库写入需求时不升级 schema。确有迁移必要时必须解释原因并验证旧库无损升级。

保留现有 `VocabularyApp.backupState` 和 metadata 表。新设置/缓存必须有应用命名空间；不枚举、读取或清理其他应用的存储。GitHub Pages 同主机的不同项目路径仍共享 Origin，命名空间减少冲突，不构成安全隔离。

本阶段不引入 Service Worker，不调整现有 Pages 项目路径，不迁移域名。

## 8. 输入法、手机与性能

- 沿用现有组合输入保护；IME 候选确认的 Enter 不得误触发查询或保存。
- Ctrl/Meta+K 的现有搜索聚焦行为与弹窗上下文保持正确，不新增浏览器快捷键冲突。
- 候选列表可以用键盘访问；状态反馈适合辅助技术读取，焦点不能随异步响应跳走。
- 1440px 桌面与 360px 窄屏验证布局；在实际手机检查软键盘、按钮可达性、长释义滚动和关闭弹窗。
- 补真实 Windows 中文输入法候选操作，记录输入法和浏览器；无法操作物理输入法时明确列为未验证，不用事件模拟代替结论。
- 万词完整 DOM 性能作为单独观察项，不与在线接口耗时混淆。当前 30 词使用无需先引入虚拟列表；只有测得实际卡顿才讨论分页或其他优化。

## 9. 验收清单

功能自动化使用可控响应，真实来源另外做少量冒烟测试；不能让日常 CI 依赖第三方在线稳定性，也不能只用模拟响应证明真实来源可用。

| 场景 | 验收结果 |
| --- | --- |
| 本地输入与组合输入 | 未点击查词不产生第三方请求；IME Enter 不误触发 |
| 查询成功 | 来源与语言准确显示，用户可选择、编辑再保存 |
| 已有未保存释义 | 查询保留内容，采用候选须明确处理替换 |
| 无结果/短语不支持 | 提示明确，仍可手动新增 |
| 离线、超时、429、异常 JSON | 可恢复，输入保留，本地检索和导出不受影响 |
| A 查询慢于 B、编辑查询词、关闭弹窗 | 过期结果不覆盖当前状态 |
| 查询/选择/取消 | 数据和备份 revision 均不变 |
| 确认保存/保存失败/重复 | 成功仅按现有语义更新一次；失败和重复不写入；全库去重 |
| 连续添加 | 前一词的请求和候选不进入下一词，焦点与状态正确 |
| 多标签页并发保存 | 唯一约束和事务维持，重复提示可恢复 |
| 第三方异常文本或链接 | 不执行 HTML/脚本，不开放不安全链接 |
| JSON 往返 | 保存后的词条可导出、导入，兼容 version 1 |
| 已有功能回归 | CRUD、筛选、排序、复制、导入预览、备份提醒和迁移仍通过 |
| 线上与产物 | Pages 子路径和实际查词路径正常；dist 无密钥、个人词库或测试输出 |

测试使用独立数据库/浏览器 Profile 和合成数据，不操作或清理用户日常词库。已导入的 30 词会被识别为重复；测试新增应使用独立环境或新的测试词，不要求用户删除现有记录。

## 10. 版本、发布与报告

3A 只有评估文档时，不升级应用、不创建 `v1.2.0`，不将评估记作功能发布。

3B 成功交付后：

1. `package.json` 与锁文件同步升级到 `1.2.0`；数据库与 JSON 版本独立管理。
2. 遵循仓库现有检查与 CI 门槛，保留有效测试；确需依赖变动时说明用途和代价。
3. 实际部署沿用既有项目流程，并遵循开发任务中已有的用户授权；本方案本身不执行发布。
4. 本地与部署验收通过后创建并推送新的注释标签 `v1.2.0`，指向已验收的应用提交，不移动既有标签。
5. 报告写入 `docs/stage2-part3-report.md`，记录来源选择、实测覆盖、费用与许可依据、数据/网络行为、测试结果、未验证事项、应用提交、CI 与标签状态。

报告不能把英文参考称为中文词典、把模拟结果称为真实接口验证、把下载发起称为备份落盘、把命名空间称为 Origin 隔离，或把未完成的 3B 记为完成。

## 11. 开发交接要求

后续开发对话从同一项目开始，先读取当前代码、适用的项目指令、README、项目背景、本方案和 Part 2 完成报告，检查工作区，保留用户已有文件，不重新初始化项目或复制出嵌套项目。

第一项具体任务是完成来源评估报告。可独立完成的公开文档核对、无费用试查、响应分析及测试设计持续推进；确需账户、密钥、付费或新服务资源时，把已完成的评估与具体选择交给用户，不让用户在没有依据时先选服务。

3B 按“单一来源 → 最小查询流程 → 请求与保存保护 → 回归和真实环境验收”顺序实施。专业标签、论文来源与原句列入后续阶段，不混入本次发布。
