## 2. 用户最初的目标

用户是电子信息专业本科生，在阅读英文文献时遇到较多陌生单词、专业术语和短语，希望逐渐积累个人英文专业词库。

核心流程是：读论文遇到生词 → 搜索个人词库 → 已收录则查看释义并加深印象 → 未收录则手动添加英文与中文释义 → 后续继续检索、修订与整理。

最初明确提出的功能包括：

- 添加英文和中文释义，并保留编辑能力。
- 删除不需要的记录，减少日常查找负担。
- 支持部分搜索：短语输入其中一个词，长单词输入前几个字母也能找到。
- 按 A–Z 分类浏览，例如点击 A 查看 A 开头的词。
- 后续可以考虑接入词典，减少在外部查词再手工输入的步骤。

专业语境是重要背景。词典未来应提供候选释义，由用户选择、修改并确认加入个人词库；多义词不能仅凭通用释义自动决定保存内容。

## 3. 使用方式、成本与产品方向

用户多次关注以下问题：关闭网页后数据是否还在、词库是否存入项目文件夹、JSON 是否相当于备份、GitHub 保存什么，以及本地保存数据是否需要额外费用。

用户希望项目后续能够像公开网页小游戏一样，任何拿到网址的人直接打开使用，而不只在自己的电脑上运行。公开提供应用界面与共享个人词库是不同目标：当前采用公开网址、各浏览器环境各自保存本地词库的路线。

规划强调简单、稳定、快速、可以每天使用，优先避免业务服务器、云数据库和付费 API。这里记录的是历史目标与成本考虑，不是对未来第三方服务价格或政策的永久保证。

## 4. 已选定的基础方案

- 项目目录明确为 `D:\VocabularyApp`。早期建议中的 `D:\Projects\VocabularyApp` 已被后续路径决定替代，不创建额外嵌套目录。
- 技术栈为 React、TypeScript、Vite、Dexie、IndexedDB。
- Node.js 用于开发、构建和静态预览，不是业务后端。
- UI 通过 Service / Repository 访问数据，避免 React 组件到处直接写 Dexie。
- 词条使用稳定 ID，保留创建/修改时间、学习状态和查看统计。
- 数据库版本化管理；升级保留旧词库，不通过删库重建解决兼容问题。
- 代码模块化且不过度工程化，不为未来可能的功能提前加入大量无用抽象。

现有词条模型包括 `id`、`word`、`meaning`、`note`、`status`、`searchCount`、`createdAt`、`updatedAt`、`lastSearchedAt`。后续正式规则已明确：`searchCount` 和 `lastSearchedAt` 表示真正打开详情的次数与时间，不是输入搜索或结果出现次数。

## 5. 数据、备份与代码的边界

| 内容 | 已采用的职责 |
| --- | --- |
| `D:\VocabularyApp` | 程序代码、配置和项目文档 |
| 浏览器 IndexedDB / `VocabularyDB` | 日常使用的词库主数据 |
| 用户主动导出的 JSON | 外部备份与迁移文件 |
| Git / GitHub Repository | 代码版本与远程代码保存 |
| GitHub Pages | 提供构建后的网页资源 |

JSON 不是日常主数据库，不是每次添加后自动写出的磁盘文件。`backups` 仅是用户可手工整理备份的预留目录；下载不自动写入该目录。

个人词库、真实备份、浏览器 Profile、凭据不默认进入 GitHub 或部署产物。复制项目目录或 `git clone` 不会同时迁移浏览器词库。

换浏览器、设备、Profile 或 Origin 时，通过 JSON 导出/导入迁移。localhost 与 Pages 存储独立；清理网站数据等操作可能导致本地数据丢失，因此需保留外部备份。

导出只能记录“发起下载”，不能声称已确认文件成功保存。浏览器持久存储也不能替代外部备份。

## 6. 核心交互原则

- 一个搜索框统一检索英文、中文释义和备注，支持大小写忽略、前缀及包含匹配。
- A–Z、`#`、状态与搜索可以组合；筛选无结果不等于词库丢失。
- 英文同名判断采用首尾空格去除与小写归一化；显示保留合理大小写。
- 熟悉的词可标记为“已掌握”，默认主要查看学习中；同时保留带二次确认的永久删除。
- JSON 合并导入保护当前库，同名词保留目标库内容，不能默认覆盖整个词库。
- 界面简洁、适合长期阅读，桌面优先并兼顾手机宽度。
