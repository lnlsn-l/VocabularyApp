## 3. 数据模型、迁移与 JSON 兼容

### 3.1 保持词条业务语义

现有 `VocabularyEntry` 继续包含：

```text
id
word
meaning
note
status
searchCount
createdAt
updatedAt
lastSearchedAt
```

本阶段不因 UI 优化改变这些字段的业务语义。`status` 继续使用 `learning` / `mastered`。`searchCount` 表示真正打开词条详情的次数；`lastSearchedAt` 表示最后打开详情的时间，不把搜索输入或结果展示计为查看。

内部 `normalizedWord` 去重索引不进入业务展示或 JSON 备份。英文去重规则保持 `trim + lowercase`；不新增词形归并或内部空格归一化规则。

### 3.2 应用元数据单独保存

备份状态、提醒状态和 UI 偏好属于应用级 metadata/settings，不放入每条 `VocabularyEntry`。

如确有需要，允许 Dexie 从 `version(1)` 升级到 `version(2)`，新增独立应用元数据表。本阶段这一有限升级已在需求范围内，无需仅因新增该表再次询问；必须提供 upgrade/migration 或可靠兼容方案，并测试旧词库无损保留。

迁移必须保留旧词条的 ID、英文、释义、备注、状态、统计和全部时间字段，保留去重约束，不删除数据库。新元数据的初始值必须合理，不能把已有非空词库误报为已完成外部备份。

也可使用合理的独立非业务存储方案而不升级 schema，但必须说明可靠性、并发更新、多标签页一致性和失败处理。

### 3.3 区分三类版本

| 版本 | 本阶段要求 |
| --- | --- |
| 应用 package version | 完成功能并发布为 `1.1.0` |
| Dexie schema version | 可保持 1；确有需要时无损升级到 2 |
| JSON backup format version | 保持 `version: 1`，兼容第一版和当前在线版 |

不能因数据库增加 metadata 表而机械升级 JSON 格式版本。

备份 JSON 继续描述用户词库，不加入 `lastExportRequestedAt`、`dataRevision`、提醒关闭状态、排序偏好等应用 UI 元数据。外层格式保持兼容：

```json
{
  "version": 1,
  "exportedAt": "2026-10-07T00:00:00.000Z",
  "app": "VocabularyApp",
  "entries": []
}
```

该示例仅说明现有结构。真实 entries 继续保留现有可备份字段；不得用示例替换真实数据。

## 4. 备份状态系统（必做）

### 4.1 用户可见状态与措辞

提供轻量的备份状态区域，至少显示：

- 最近一次发起 JSON 导出的时间；从未记录导出时显示“尚未发起导出”或等价准确措辞。
- 当前词库自上次发起导出后是否发生变化。
- 立即导出 JSON 的入口。

时间以用户可读的本地时间显示。统一使用“最近发起导出”，不使用“最近成功备份”“备份已成功保存”或“文件已安全保存”。

导出反馈建议统一为：

> 已发起 JSON 下载，请在浏览器下载列表中确认文件已保存。

应用只能知道发起了下载，不能确认最终磁盘目录、用户是否删除文件或是否保留其他设备上的副本。

导出仍覆盖整个词库，不受当前搜索、状态或字母筛选影响。保持原有文件命名和下载行为，不默认写入 `D:\VocabularyApp\backups` 或任意磁盘目录。

### 4.2 可靠的变更识别

不能仅根据当前词条的最大 `updatedAt` 判断是否需要备份，因为删除后的记录已不存在，导入和统计变化也需要准确处理。

推荐使用下列应用级元数据，或提供行为等价且可靠的方案：

| 字段 | 含义 |
| --- | --- |
| `dataRevision` | 成功写入可备份数据变化后的修订号 |
| `lastExportedRevision` | 最近发起导出时，实际导出快照对应的修订号 |
| `lastExportRequestedAt` | 最近成功发起下载请求的时间 |

每次真正改变可备份数据后更新 revision；失败、取消和纯读取不更新。至少覆盖新增、编辑、状态修改、永久删除、成功导入新词条。

仅打开详情这个 UI 动作本身不额外计为内容编辑；但现有查看动作会写入 `searchCount` / `lastSearchedAt`，且这两个字段进入 JSON，因此这些实际统计写入也计入可备份数据变化。保持原有查看计数语义，不把查看写成内容 `updatedAt` 修改。

提醒策略与 revision 分开控制，避免用户频繁查看详情导致频繁提醒。新增/修改/删除的分别计数可以作为可选展示；若未准确维护此类计数，不从 revision 差值推断具体操作数量。

没有发生数据变化的操作不制造未备份状态。全重复或全无效且没有写入的导入不增加 revision。导入新增词条后必须显示未备份变化，不能因为导入源是 JSON 就认定当前合并后的词库已有完整外部备份。

### 4.3 导出一致性与持久化

备份状态必须刷新后仍合理，并能反映同 Origin 多标签页的数据变化。词条写入与 revision 更新应可靠关联，不能在写入失败时把变化记为成功，也不能因多个标签页更新丢失变化。

导出时，`lastExportedRevision` 必须对应实际 JSON 快照。快照读取后若又发生写入，不能把快照之外的新变化标为已导出。解析、序列化或下载请求失败时，不更新为已发起导出。

发起导出且之后没有新变化时，可以表示“自上次发起导出后无新增变化”，仍不能宣称外部文件已经保存。关闭提醒不能修改 `lastExportedRevision` 或伪造导出时间。

对于升级前已存在但没有备份 metadata 的词库，不猜测历史导出时间；说明采用的初始化规则和状态含义。全新空词库不得出现错误的紧急备份提醒。

## 5. 备份提醒与数据说明（必做）

### 5.1 提醒触发与关闭

使用非模态提示、小型 banner 或数据说明区域，不强制弹窗，不阻塞搜索、添加或编辑，不在每次打开页面或每增加一个词后打断用户。

触发条件必须首先存在未导出变化，再结合合理的时间或累计变化阈值。原讨论中的候选为 14 天或 50 次内容变化，均是示例，不是未经评估就必须写死的参数。

开发者应选择简单、集中配置且容易解释的规则，并在文档与报告说明：

- 时间阈值与变化阈值如何组合。
- 从未发起导出、已有旧词库、空库分别如何处理。
- 查看统计与主要内容变化怎样影响提醒，为什么不会频繁打断。
- “本次关闭”或“稍后提醒”的作用范围、恢复条件以及是否持久化。

用户必须能够关闭当前提醒。关闭只是暂时忽略，不代表备份完成；避免关闭后同一提醒立即反复出现。

### 5.2 数据帮助文案

在现有“数据说明”或备份区域，用简洁文字明确：

- 主数据保存在当前浏览器/Profile 的 IndexedDB。
- JSON 导出是外部备份方式；点击只代表发起下载。
- 文件通常在浏览器下载目录，也可能由用户选择目录；应用无法确认最终位置。
- GitHub 仓库和 GitHub Pages 不会自动保存用户的个人词库。
- 换设备、换浏览器或清理网站数据前应先导出并确认保留文件。
- 本阶段没有自动云备份或跨设备自动同步。

## 6. 浏览器持久存储（可选增强）

允许评估或实现 `navigator.storage.persist()`；它不是本阶段核心完成条件。若实现，可以提供轻量入口或在合适时机请求，并检测相关 API 是否存在，处理浏览器拒绝和异常。

若有 UI，清楚区分“已允许”“未允许”“当前浏览器不支持”；失败不能导致应用不可用。

UI 和文档必须说明：持久存储只能降低浏览器主动回收数据的可能性，不能防止用户主动清除网站数据，不能替代 JSON 外部备份，也不能承诺“数据绝对不会丢”。

最终报告记录是否实现、请求时机、实际验证的浏览器与结果。没有实际验证的浏览器行为标为未验证，不推断全部浏览器都一致。

## 7. JSON 导入预览与冲突分析（必做）

### 7.1 完整流程

```text
选择 JSON 文件
→ 解析
→ 验证格式与记录
→ 读取当前词库并分析
→ 展示预览
→ 用户确认
→ 再次读取和校验当前状态
→ 必要时更新预览并再次确认
→ 在事务中安全合并
→ 显示实际结果
```

从选择文件到预览、查看差异、取消为止，均不得写数据库：不生成真实词条、不更新时间、不改变查看统计、不改变 backup revision。取消后数据库和备份状态保持原样。

保持现有 UTF-8 BOM 支持、文件大小限制和结构校验；上一阶段报告记录单文件上限为 20 MB，开发前核对实际代码，不在本阶段无理由放宽。

非法 JSON、不支持的版本或错误外层结构拒绝整个文件并给出可读说明。合法外层中的无效记录按原规则跳过并统计。

### 7.2 预览至少显示

| 信息 | 要求 |
| --- | --- |
| 文件名 | 让用户确认选择的文件 |
| 备份导出时间 | 从文件的现有字段读取，不伪造缺失时间 |
| JSON 格式版本 | 明确展示并验证兼容性 |
| 文件中有效词条总数 | 明确统计口径，说明是否包含重复 |
| 当前词库总数 | 全库数量，不受页面筛选影响 |
| 预计新增 | 确认合并后会新增的数量 |
| 预计重复 | 已有同名词与文件内重复的统计 |
| 预计无效 | 被跳过的无效记录数量 |
| 重复中存在内容差异的数量 | 作为重复的子集，不重复加到总数 |

文件内重复应能识别并统计，可作为总重复数量的细分。必要时同时显示文件原始记录数，确保新增、重复、无效与有效数量的定义可核对，不使用互相重叠却看似可相加的分类。

预览必须提供“取消”“确认合并”，并允许查看重复词的差异。持续明确“同名词保留当前词库版本，不覆盖”。

### 7.3 差异比较与展示

去重仍以 `word.trim().toLowerCase()` 或现有等价实现为准，显示保留合理原始大小写。

对同名词至少比较 `meaning`、`note`、`status`，展示当前库与备份文件的差异及最终保留的一方。例如：

```text
substrate

当前词库：衬底；基板
备份文件：衬底
处理：保留当前词库版本
```

可选比较 `searchCount`、`createdAt`、`updatedAt`、`lastSearchedAt`；不为此把预览做成复杂编辑器。报告中明确“存在差异”的字段集合。

本阶段不提供逐条选择覆盖或自定义 merge。差异展示用于解释安全合并会发生什么，默认处理规则不变。

### 7.4 保持现有安全合并规则

| 情况 | 必须保持的行为 |
| --- | --- |
| 有效新词 | 新增到当前词库，保留有效备份元数据 |
| 当前库已有同名词 | 跳过，保留当前库内容，不覆盖释义、备注、状态或统计 |
| 文件内部同名重复 | 只接受第一条符合规则的有效新记录，其余计为重复 |
| 单条无效记录 | 跳过并计入无效数量 |
| 不同词发生 ID 冲突 | 按现有规则给新词重新分配 UUID，保护旧记录 |
| 导入中途失败 | 整个合并事务回滚，不留下部分写入或错误 revision |

继续兼容第一版本地版、第二阶段第一部分在线版导出的 JSON `version: 1`。

### 7.5 预览后的并发变化

预览不能作为实际写入的唯一依据。同 Origin 其他标签页可能在预览打开期间新增、编辑或删除词条。

点击确认时必须重新读取当前数据库，重新校验重复、差异和 ID 冲突；实际写入事务继续保护唯一性和回滚。复用分析规则或等价共享逻辑，避免预览与导入采用不同判定。

若新增/重复数量、差异或实际处理结果发生重要变化，更新预览或明确展示变化并要求重新确认，不盲目按过期预览写入。报告说明重要变化的判定规则和实现方式。

完成后展示实际新增、重复、无效数量；若没有实际写入，不制造数据变化。成功新增后计入未备份变化，不能将输入 JSON 当作合并后全库的最新外部备份。

## 8. 筛选与排序反馈（必做）

### 8.1 当前条件摘要

保持搜索、状态、字母筛选和排序可组合。以紧凑摘要或可移除条件标签显示当前生效条件，例如：

```text
当前筛选：[学习中 ×] [E ×] [electro ×]
找到 8 条 / 共 1268 条
```

每个筛选条件可单独清除，清除搜索不影响状态或字母，清除状态恢复全部状态，清除字母恢复全部字母。提供“清除全部”，清空搜索、恢复全部状态和全部字母，保留排序选择，与现有清除筛选语义一致。

总词条数始终指全库数量。区别“全库为空”和“当前条件无结果”，让用户容易发现列表为空是筛选造成的。

### 8.2 排序规则与少量结果说明

保留现有排序及稳定比较规则：

| 排序 | 用户可理解的含义 |
| --- | --- |
| 英文 A–Z | 按英文名称排序，忽略大小写差异 |
| 最近添加 | 创建时间从新到旧 |
| 最近查看 | 最后打开详情时间从新到旧，未查看记录靠后 |
| 查看次数最多 | 打开详情次数从多到少 |

指标相同后继续按英文和稳定 ID 比较。提供可发现的简短排序说明；当前结果为 0 或 1 条时，显示“当前结果少于 2 条，排序不会产生可见变化”或等价非模态反馈。

### 8.3 持久化边界

本阶段不持久化临时搜索文本，刷新后不恢复 `electro` 之类查询。默认不跨刷新恢复状态或字母筛选，避免遗留条件造成数据丢失的误解；保持现有首次打开的默认行为，并展示其生效状态。

可选保存最近使用的排序偏好，前提是实现简单可靠。保存的任何 UI 偏好都必须遵守应用命名空间规则，并在报告说明。不要加入无关的设置中心。

## 9. 阅读时的添加与复制效率（必做）

### 9.1 无结果直接添加

用户搜索 `anisotropic` 且没有结果时，提供“添加 ‘anisotropic’”入口。点击后打开现有新增表单，英文字段预填当前搜索原文，保留合理大小写，并继续使用现有首尾空格校验和去重规则。

不能因为组合筛选下没有结果就认定全库一定没有该词。真正保存前仍执行完整重复检测，存在同名词时使用现有提示/查看入口，不能绕过去重。

### 9.2 连续添加

新增模式同时提供“保存”“保存并继续添加”。原“保存”保留现有正常保存行为。

“保存并继续添加”成功后：

1. 完成当前词条写入，并更新列表和备份状态。
2. 清空 `word`、`meaning`、`note` 和当前表单错误。
3. 状态恢复合理默认值，沿用新增默认“学习中”。
4. 保持新增弹窗打开，焦点回到英文输入框。
5. 给出简短成功反馈，允许继续录入下一条。

保存失败或遇到重复时保留全部表单内容，不关闭、不清空，不增加错误 revision。写入中防止重复提交，连续录入不能绕过数据层去重。

编辑现有词条时不显示“保存并继续添加”，只保留“保存”“取消”等现有编辑操作。

### 9.3 复制动作

词条详情提供“复制英文”“复制中文释义”的轻量入口。使用 `navigator.clipboard` 时检测支持情况，并处理权限拒绝和复制异常。

成功显示短暂“已复制”；失败提供清楚可读的反馈，不能影响详情、编辑、搜索或其他功能。按钮应有明确可访问名称，不使用无 label 的图标。

可选提供“复制完整词条”，例如 `substrate — 衬底；基板`，仅在实现简单时加入。优先完成英文和释义两个必做动作。

## 10. 快捷键、Enter 与中文输入法（必做）

### 10.1 搜索聚焦

提供可发现的搜索聚焦快捷操作，例如 `Ctrl + K`，或其他合理且与浏览器常用操作冲突较小的组合。聚焦搜索框时不自动清空已有查询。

最终组合应经过实际浏览器检查，并在 UI/README 提供简短提示。不要让全局快捷键在不适当的弹窗或输入上下文中破坏正在进行的操作。

### 10.2 添加快捷键（可选）

可增加打开新增表单的快捷键，但不未经评估抢占 `Ctrl + N` 等浏览器标准新窗口操作。优先选择冲突较小且容易发现的组合。

全局添加快捷键不是强制项；可以仅完成无结果一键添加。报告说明是否实现及选择理由。

### 10.3 IME 与 Enter

所有自定义快捷键及 Enter 行为必须正确处理中文 IME composition。用户正在组合输入或选词时，Enter 不能误触发搜索结果打开、表单提交、保存或其他应用操作。

使用 `compositionstart`、`compositionend`、`event.isComposing` 或等价可靠机制，覆盖当前表单提交路径；不能只保护某个快捷键而让原生提交路径误保存。

正常非组合输入状态下保留现有合理的 Enter 行为。测试需覆盖中文选词与组合结束附近的事件顺序，实际检查输入体验。

### 10.4 Esc、焦点与无障碍

新按钮、预览和 dialog 必须键盘可访问。保留原生 dialog 的合理焦点管理；Esc 能关闭或取消弹窗，关闭后焦点返回合理位置。

预览关闭不能触发导入，删除弹窗取消不能删除。焦点管理不得破坏 IME 选词和正在进行的输入。

## 11. UI、移动端与性能

### 11.1 保持现有设计

不整体重做视觉风格，沿用现有设计语言，只增加必要的备份状态、导入预览、筛选摘要、快捷操作和按钮，避免界面拥挤。

继续在约 1440px 桌面和 360px 手机宽度可用。备份状态及导出、导入预览、差异查看、连续添加、复制、筛选清除均需在移动端正常操作；手机用户不能依赖键盘快捷键完成核心流程。

### 11.2 避免明显低效的分析

导入预览尽量构建 `normalizedWord → current entry` 内存映射，或使用现有等价高效访问方式。不要对每条导入记录反复扫描整个词库，避免意外 O(n²) 比较。

目标是在几千至一万级词条时保持合理体验，不要求新增复杂虚拟列表或专业 benchmark。

使用 1000、5000、10000 条程序化数据做基础验证，至少覆盖搜索、筛选、导入预览分析，记录数据规模、环境与基本结果。区分这些基础测试与尚未验证的大规模/长期性能，不给出未经测试的性能保证。

## 12. GitHub Pages 同 Origin 存储命名空间（必做）

正式网站为 `https://lnlsn-l.github.io/VocabularyApp/`。以下项目路径具有同一个 Origin `https://lnlsn-l.github.io`：

```text
https://lnlsn-l.github.io/VocabularyApp/
https://lnlsn-l.github.io/ProjectA/
https://lnlsn-l.github.io/ProjectB/
```

IndexedDB、localStorage 等站点存储主要按 Origin 隔离，URL path 不构成独立的存储安全边界。应用级命名用于避免命名冲突和误清理，不构成同 Origin 应用之间的访问安全隔离；不能宣称加前缀后其他同源应用无法访问。

本阶段只做命名和边界保护，不迁移域名或更换部署位置；仍按现有流程发布本阶段功能到 Pages。

### 12.1 名称审查

检查并记录当前和新增的：

- Dexie 数据库名称及表用途。
- localStorage key。
- sessionStorage key。
- metadata/settings 所在数据库、表以及相关记录 key。
- 备份状态、提醒关闭状态、排序偏好等新增持久化名称。

保留已有 `VocabularyDB` 名称；它已经明确标识词库应用，不为命名优化而重命名，否则可能使老用户看起来像数据丢失。

新增浏览器存储必须属于清晰的 VocabularyApp 命名空间，例如：

```text
VocabularyApp.settings
VocabularyApp.backupState
VocabularyApp.reminderState
VocabularyApp.sortPreference
```

若使用 `VocabularyDB` 内独立 metadata/settings 表，数据库本身必须提供明确应用归属；在文档记录完整层级，并为新增应用元数据记录使用清楚的应用专属名称或等价方案。

不要在 Origin 级存储中新增 `settings`、`metadata`、`config`、`appData` 这类通用 key。上述示例不要求全部采用，按实际设计选择一致且清楚的名称。

### 12.2 清理边界

- 不访问、修改或删除同 Origin 下未知的其他数据库或 storage key。
- 任何“清除本应用设置”操作只能处理 VocabularyApp 明确拥有的名称，不扩大到整个 Origin。
- 禁止 `localStorage.clear()`、`sessionStorage.clear()` 或全局枚举数据库后批量删除等可能影响其他应用的操作。
- 不删除现有 `VocabularyDB`，不通过清空站点存储进行迁移。
- 测试确认新增 metadata/settings 不使用通用 Origin 级 key；涉及清理时确认其他应用的测试 key 保留。
- 在阶段报告列出本项目实际使用的全部浏览器持久化存储名称和命名空间；sessionStorage 如有使用也列出。

## 13. 本地数据与安全边界

不引入远程词库上传、第三方分析 SDK、用户追踪、广告或外部业务 API。个人词库仍只保存在当前浏览器环境的 IndexedDB，导出由用户主动下载。

`navigator.storage.persist()` 和 `navigator.clipboard` 属于本阶段允许的浏览器能力，不需要业务后端。

localhost 和 Pages 的 Origin 不同，继续通过 JSON 手动迁移；同 Profile 同 Origin 多标签页共用数据，独立 Profile 仍各自隔离。不要把公开网页等同于公开个人数据，也不声称本阶段实现身份认证或自动同步。
