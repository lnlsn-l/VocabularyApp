## 一、项目目标与适用场景

VocabularyApp 是面向英文文献阅读的个人专业词库，主要服务于电子信息相关专业的单词、术语和短语积累。

应用解决的是日常阅读中的一个具体问题：遇到陌生英文内容时，快速查找自己以前记录的中文释义；没有收录就手动添加，并在后续阅读中不断修正释义和备注。熟悉的词条可以标记为已掌握，仍保留在词库中，供以后查阅。

第一版的目标是建立一条可以长期重复使用的完整流程：

```text
阅读英文文献
    ↓
搜索个人词库
    ↓
已有词条 → 打开详情 → 查看释义与备注 → 记录查看次数
未收录词 → 添加英文与中文释义 → 保存到 IndexedDB
    ↓
继续阅读、编辑释义、标记已掌握
    ↓
定期导出 JSON 备份
```

优先级依次为数据保存可靠、检索方便、添加快捷、代码易维护和界面清晰。当前产品适合个人手动整理专业词库，不依赖在线词典或自动翻译服务。

## 三、页面组成与日常使用

### 3.1 首页

首页包含应用名称、添加入口、导入／导出入口、统一搜索框、学习状态筛选、字母分类、结果数量、排序选择和词条列表。

默认显示“学习中”，方便把注意力放在尚未掌握的词条上。界面提供“全部”和“已掌握”入口，已掌握词条不会因退出默认列表而被删除。

结果数量采用“当前结果数 / 总词条数”的形式。例如 `0 / 1` 表示当前搜索或筛选没有结果，但整个词库仍有一条记录。

### 3.2 添加词条

点击“添加词条”，填写英文词汇或短语、中文释义、可选备注和学习状态。状态默认为“学习中”。

英文和中文释义为必填项。点击“保存”并写入成功后，词条立即进入 IndexedDB，列表自动更新，不需要刷新页面。这里的保存是提交表单后的数据库写入，不是用户每输入一个字符就自动保存草稿。

当搜索框中输入的是普通 ASCII 内容时，新增表单会将该查询内容预填为英文词条，减少重复输入。

### 3.3 查看与编辑

点击列表中的英文标题打开详情，查看完整释义、备注、学习状态、查看次数以及创建、修改和最后查看时间。

点击“编辑”或详情中的“编辑词条”可修改内容。编辑时自动填入原内容，保存后更新最后修改时间，并保留原有创建时间和查看统计。

### 3.4 标记掌握与永久删除

“标记已掌握”将状态设为 `mastered`；“重新学习”将状态恢复为 `learning`。这两种操作都保留词条，并更新修改时间。

永久删除需要再次确认。点击“取消”或取消弹窗不会删除数据；确认后记录从数据库中移除。第一版没有回收站或撤销删除功能，恢复需要依赖删除前的 JSON 备份。

## 四、已实现功能与规则

### 4.1 输入校验与去重

保存前对英文、中文释义和备注进行首尾空格清理。重复判断采用英文内容的 `trim + lowercase`，例如 `substrate`、`Substrate` 和 ` SUBSTRATE ` 视为同一个词。

显示时保留用户输入的大小写。内部空格不做自动合并，也不进行词形还原，因此 `carrier mobility` 和 `carrier  mobility`、单复数等变化目前不会自动视为同一词。

重复校验同时用于新增和编辑。编辑一个词条时允许保留自己的英文名称，但不允许改成另一个现有词条的名称。重复提示提供“查看已有词条”入口。

数据库还设置了唯一索引，并将新增与修改置于事务中，因此并发操作也不能绕过去重规则。

### 4.2 搜索

一个搜索框同时匹配 `word`、`meaning` 和 `note`，输入后实时更新结果。查询内容去除首尾空格，英文忽略大小写；各字段采用部分字符串匹配。

| 搜索类型 | 示例 | 当前行为 |
| --- | --- | --- |
| 英文完整匹配 | `substrate` | 找到该词 |
| 英文前缀匹配 | `sub` | 找到 substrate |
| 英文部分匹配 | `strate` | 找到 substrate |
| 短语中间部分 | `interference` | 找到 electromagnetic interference |
| 中文部分匹配 | `电磁`、`干扰` | 匹配中文释义 |
| 备注匹配 | 备注中的专业领域或语境 | 匹配备注内容 |
| 大小写变化 | `sub`、`SUB`、`Sub` | 效果一致 |

第一版没有模糊拼写纠错、同义词扩展、正则搜索或英文词形分析。当前方式简单直接，适合先积累个人词库。

### 4.3 字母分类与状态组合

分类提供“全部字母”、`#` 和 A–Z。分类依据是去除首尾空格后词条的第一个字符：英文 A–Z 进入对应字母；数字或特殊字符开头进入 `#`。短语按整个短语的开头分类。

搜索、字母和学习状态按照“同时满足”组合。例如“学习中 + E + electro”只显示符合三项条件的词条。“清除筛选”清空搜索、恢复全部字母和全部状态，保留当前排序选择。

交付后已按使用反馈调整空状态图标：

| 当前分类 | 没有匹配结果时的图标 |
| --- | --- |
| A–Z 中的某个字母 | 当前选中的字母，例如 K |
| `#` | `#` |
| 全部字母 | `Aa` |

图标表达的是当前分类。即使无结果由搜索词或状态造成，只要选中了某个字母，仍显示该字母。

### 4.4 排序

排序作用于当前搜索及筛选后的词条，不会取消筛选，也不会改变数据库内容。

| 选项 | 实际排序规则 |
| --- | --- |
| 英文 A–Z | 英文名称排序，忽略大小写差异 |
| 最近添加 | 创建时间从新到旧 |
| 最近查看 | 最后查看时间从新到旧；没有查看时间的排在后面 |
| 查看次数最多 | 查看次数从多到少 |

排序指标相同时，继续按英文名称排序，并以稳定 ID 作最终比较，保持结果稳定。编辑不会把词条变成“最近添加”，因为创建时间不变。

交付后的复查已使用添加时间、查看时间和查看次数各不相同的三条独立测试词，通过页面下拉框验证上述排序。当前结果为零条或一条时，切换排序不会有可见位置变化；多个词条指标相同时，也可能保持相同顺序。

### 4.5 查看统计

`searchCount` 的业务含义是“真正打开词条详情的累计次数”。尽管字段名带有 search，它不是搜索框输入次数，也不是出现在结果中的次数。

只有点击英文标题打开详情，或通过重复提示中的入口查看已有词条时，才增加计数并记录 `lastSearchedAt`。搜索、显示结果、编辑、状态切换、页面刷新和详情关闭不会增加次数。

查看统计使用数据库事务更新，已验证并发查看不会丢计数。查看行为不修改 `updatedAt`，这样“修改时间”仍表示内容或状态的修改。

### 4.6 状态反馈与错误处理

当前处理了加载、整个词库为空、筛选无结果、保存成功、状态更新、删除完成、导入统计和导出提示。

输入为空、重复词条、存储初始化失败、写入失败、修改／删除失败、文件无法读取、JSON 无法解析、不支持的版本及结构错误都会显示普通用户可理解的提示。保存失败保留表单内容；初始化失败提供重试；删除失败在确认弹窗中显示错误。

弹窗支持取消和 Esc 操作，使用浏览器原生 dialog 管理焦点。异步保存和删除期间相关按钮会禁用，以减少重复提交。

## 五、词条数据模型

| 字段 | 类型 | 含义与维护方式 |
| --- | --- | --- |
| `id` | string | 稳定记录 ID；应用新增时生成 UUID |
| `word` | string | 英文单词、术语或短语，必填 |
| `meaning` | string | 用户维护的中文释义，必填 |
| `note` | string | 备注，可为空字符串 |
| `status` | learning / mastered | 学习中或已掌握，默认学习中 |
| `searchCount` | number | 实际详情查看次数，新增时为 0 |
| `createdAt` | string | 创建时间，新增时生成 ISO 时间 |
| `updatedAt` | string | 内容或状态最后修改时间 |
| `lastSearchedAt` | 可选 string | 最后打开详情的时间，未查看时可以不存在 |

数据库内部另有 `normalizedWord` 字段，用于不区分大小写的唯一索引。该字段不向页面数据模型和 JSON 备份暴露。

应用生成的 ID 为 UUID；导入时接受有效的非空字符串 ID。导入的新词若与已有的另一词条发生 ID 冲突，会生成新的 UUID，避免覆盖原记录。

## 六、数据保存、备份与恢复

### 6.1 三类内容分别保存

| 内容 | 保存位置 | 是否默认进入 GitHub |
| --- | --- | --- |
| 程序代码和配置 | `D:\VocabularyApp` | 是 |
| 个人词库主数据 | 当前浏览器的 IndexedDB | 否 |
| 个人词库 JSON 备份 | 用户手动选定的位置，如 `backups/` | 否 |

数据库名为 **VocabularyDB**，表名为 **vocabulary**，通过 Dexie `version(1)` 建立。数据库位于浏览器用户配置文件中的网站存储区域，而不是项目源代码目录。

React 状态只是页面中的数据呈现，IndexedDB 才是持久化主数据库。刷新和关闭页面不会主动清空数据；已经验证关闭整个浏览器进程、重新打开同一个测试配置文件后仍可读取词条。

### 6.2 Origin 与浏览器配置文件

IndexedDB 按 Origin，也就是协议、主机名和端口隔离。例如以下地址拥有不同的词库：

```text
http://localhost:5173
http://127.0.0.1:5173
http://localhost:4173
https://example.com
```

同一 Origin 下仅改变路径通常不会隔离 IndexedDB。不同浏览器、不同浏览器用户配置文件也分别保存数据。

当前开发和静态预览都固定 `localhost:5173`，启用严格端口检查，避免端口占用后自动改到其他端口。迁移地址或换电脑时，应在旧环境导出 JSON，再在新环境导入。

**GitHub 不会同步 IndexedDB；git clone 只能取得代码，不能取得或恢复个人词库。**

### 6.3 JSON 导出

点击“导出词库”会读取整个数据库，而不是只导出当前搜索、字母或状态筛选的结果。文件名按浏览器本地日期生成：`vocabulary-backup-YYYY-MM-DD.json`。

备份外层结构为：

```json
{
  "version": 1,
  "exportedAt": "2026-10-07T00:00:00.000Z",
  "app": "VocabularyApp",
  "entries": []
}
```

文件保留词条的释义、备注、状态、时间和查看统计，排除数据库内部的去重索引。

浏览器通常将文件保存到下载目录。网页不会自动写入 `D:\VocabularyApp\backups`，需要用户选择保存位置或手动移动文件。该目录已在本机预留，并整体加入 Git 忽略规则。

### 6.4 JSON 合并导入

导入先检查 JSON 可解析性、版本、应用标识、导出时间和 entries 数组，再逐条验证字段。支持 UTF-8 BOM，单文件上限为 20 MB。

| 情况 | 第一版处理方式 |
| --- | --- |
| JSON 无法解析或外层格式错误 | 拒绝整个文件，原数据保留 |
| 不是 version 1 | 拒绝整个文件 |
| 单个词条字段无效 | 跳过该条，计入无效数据 |
| 新词条 | 写入数据库，保留备份中的有效元数据 |
| 已有同名词条 | 跳过，保留当前库中的释义、状态和统计 |
| 文件内部重复 | 只导入首条有效新记录，其余计为重复 |
| 不同词条的 ID 冲突 | 给新词分配新 UUID |
| 合并中途写入失败 | 整个导入事务回滚 |

导入后显示“成功导入、重复跳过、无效数据”三项数量。

这一策略可以补回缺失词条，但不会用备份覆盖当前库中的同名词。因此恢复较旧的备份不会自动将已有词的释义、状态或统计回退到备份值。第一版没有覆盖恢复模式、导入预览或导入前自动备份。

### 6.5 日常数据保护建议

建议在集中整理词库后、批量删除前，以及更换电脑或浏览器前导出备份，并保留一份项目目录之外的副本。

持久化能力依赖浏览器正常保存网站数据。隐私模式、手动清理网站数据、删除配置文件、浏览器存储回收或系统重装都可能使本地词库消失。当前应用没有申请持久存储权限，也没有定时自动备份或磁盘自动同步。

电脑重启后的保存依据浏览器持久化存储机制；验收没有实际重启用户电脑，因此不能把跨重启测试描述为已执行。

### 7.2 数据访问分层

```text
React 页面及组件
       ↓
VocabularyService
       ↓
VocabularyRepository 接口
       ↓
LocalVocabularyRepository
       ↓
Dexie → IndexedDB
```

页面不直接操作数据库。Service 负责业务输入处理、统一错误提示和备份业务入口；Repository 负责数据库读写、唯一性检查和事务；搜索、备份解析和字段校验分别集中在工具模块中。

Dexie liveQuery 将本地数据变化传递给界面，同一浏览器同一 Origin 下的多个页面能够更新词条列表。未来若加入其他数据来源，可以沿 Repository 接口继续设计，但跨设备同步仍需要另外处理冲突和同步策略，不是简单替换接口即可完成。

schema 从 v1 起管理。未来增加字段或索引应通过新的 Dexie 版本和 upgrade 迁移，保留已有词库，不能用删除数据库作为升级手段。

## 八、运行与日常维护

### 8.1 安装和启动

```powershell
cd D:\VocabularyApp
npm ci
npm run dev
```

在浏览器打开 `http://localhost:5173/`。已经安装好依赖时，日常启动只需要执行后两条命令。

### 8.2 构建和静态预览

```powershell
npm run build
npm run preview
```

生产文件输出至 `dist/`。开发与预览使用同一端口，不能同时占用；切换前先停止旧服务。生产文件需要通过 HTTP/HTTPS 提供，不建议直接双击 HTML 文件。

### 8.3 常用检查

```powershell
npm run build
npm run lint
npm test
npm run test:e2e
git status
```

浏览器测试会自行启动服务，执行前需要释放 5173 端口。本项目测试配置使用已安装的 Google Chrome，测试词库位于独立配置文件，不会写入日常浏览器词库。

## 十二、可能的第二版优化方案

第二版建议继续围绕实际阅读流程推进，优先解决数据保护和日常操作中的具体问题。以下是候选方案与取舍，不是本次已经完成的功能，也不表示要一次性全部实施。

### 12.1 推荐优先级

| 优先级 | 方案 | 解决的问题 | 建议范围 | 相对复杂度 |
| --- | --- | --- | --- | --- |
| P0 | 备份提醒和备份状态 | 用户可能长期未导出，难以知道备份是否及时 | 展示最近一次导出时间、导出后新增／修改情况、适度提醒 | 低至中 |
| P0 | 导入预览与冲突说明 | 当前导入结果在执行后才出现，重复词直接跳过 | 先显示新增、重复、无效数量；展示重复词差异；用户确认后合并 | 中 |
| P1 | 筛选和排序反馈 | 单条结果切换排序无视觉变化，组合筛选可能不易察觉 | 当前条件摘要、排序规则说明、结果不足两条时的轻量提示 | 低 |
| P1 | 日常操作快捷化 | 阅读时反复切换和点击影响效率 | 搜索焦点快捷键、添加快捷键、连续添加、复制英文或释义 | 低至中 |
| P1 | 专业标签与来源记录 | 字母分类不能表达半导体、电路、电磁场等领域，也不能追溯语境 | 少量自定义标签、论文标题／链接和相关原句 | 中 |
| P2 | PWA 与离线启动 | 当前每次本地启动依赖命令，远程页面断网后不能可靠重新加载 | 稳定静态部署地址、应用安装入口、离线资源缓存与更新提示 | 中至高 |
| P2 | 搜索结果呈现与性能 | 词库扩大后，匹配位置和大量结果不易浏览 | 命中高亮、相关度排序评估；按实测决定分页或虚拟列表 | 中 |
| 后续独立阶段 | 跨设备同步 | 手机和电脑的数据需要手动搬运 | 单独设计认证、冲突合并、删除同步及本地离线保留 | 高 |

复杂度是结合当前结构的相对评估，不是工期承诺。第二版范围应依据一段时间的真实使用反馈确定。

### 12.2 数据保护方案的实施边界

“最近一次导出”表示应用发起了 JSON 下载，不能据此保证文件已经保存到用户指定磁盘或成功复制到其他设备。界面说明应保留这一差别。

可以评估浏览器持久存储申请并显示申请结果，但它不等于绝对不会丢失，也不能代替 JSON 备份。

导入前保存一份恢复用快照可以提升操作保护，但保存在同一 IndexedDB 中的快照仍会随网站数据清理而一起丢失。若需要外部副本，应让用户实际导出文件。

完全覆盖恢复的破坏性高于合并导入。如果后续加入，应独立入口、清楚展示影响范围、先备份并再次确认，不建议直接替代现有安全合并策略。

### 12.3 PWA 与静态部署的实施边界

PWA 可以保留纯前端架构，但需要处理首次加载、缓存更新、新旧代码与数据库 schema 兼容，以及离线状态下的资源可用性。

从 localhost 迁移到稳定域名时，Origin 会改变，必须先导出再导入词库。GitHub Private 只是代码可见性设置，不等于任何未来部署的网站也会自动私有；部署访问范围需要单独决定。

### 12.4 建议的第二版组合

**推荐的第一组改进是：备份提醒 + 导入预览 + 筛选／排序反馈 + 操作快捷化。** 这一组直接改善已经在用的流程，基本可以保留当前纯前端和本地优先架构。

如果后续使用表明词条规模和专业领域明显增加，再加入标签与来源记录。涉及数据结构变化时采用 v2 schema 迁移，旧版 JSON 备份也应继续能够导入。

如果主要痛点是启动不方便或经常使用手机，可以将 PWA 和稳定静态部署作为第二版的重点，并把备份及 Origin 迁移安排在部署之前。

在线词典辅助可以作为后续可选入口，专业释义仍由用户选择和编辑。云同步、AI 自动释义和 PDF 工具建议分别立项评估，不与第二版的小范围体验改进同时铺开。

### 12.5 第二版建议验收条件

- 原有词条、状态、备注、时间和查看统计在升级后保留。
- 第一版导出的 JSON 能在第二版中导入。
- 新功能不会让普通查询依赖登录或付费服务。
- 提醒和条件说明有实际帮助，不遮挡搜索与添加操作。
- 新的标签／来源等字段可为空，不强迫用户补齐历史词条。
- 导入预览与实际导入统计一致，遇到并发数据变化时重新校验。
- 若加入 PWA，验证首次在线使用后的离线重开、版本更新和数据库迁移。
- 性能优化以实际词库规模和测试结果为依据，避免预先引入复杂架构。
